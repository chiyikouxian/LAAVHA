# 场景区分能力与后续验证计划

日期：2026-11-09。状态：设计稿，尚未实现或运行新场景。依据见 [ALGORITHM_AUDIT.md](ALGORITHM_AUDIT.md)。

## 目标

保留三阶段遥感任务和现有基础场景，增加分别检验预测、任务权重与风险控制的场景。实验检验每个机制是否改善任务服务和迁移行为，允许强简单方法取得相同或更好的结果。场景生成依赖物理环境与外部业务，算法只获得当时可测的观测和当前任务上下文。

## 基础场景的定位

S0：现有 75 m 建筑、无额外空间阴影的主场景。用于验证业务、迁移执行、包测量、连续轨迹与基本服务接续。它不承担独自证明所有模块优势的任务。当前两次预览显示方法普遍接近两次迁移，并非实施失败。

修复算法会改变实验版本，新版本对 S0 的结果需单独保存；不得把修复后的结果与旧 30 次运行混合成一组均值。

## 场景矩阵

| 场景 | 外生变化 | 主要检验机制 | 首要观测 |
|---|---|---|---|
| S0 基础任务 | 现有几何与业务 | 端到端集成与基本接续 | 遥测/图像按时交付、原始迁移 |
| S1 持续退化与短时扰动 | 链路相关的空间阴影/干扰，具有可观测历史的变化 | 多时域预测与持续性判断 | 失效后切换、服务违约、短暂中间接入 |
| S2 服务属性冲突 | 按预设过程变化的真实背景流量和队列竞争 | 学习权重、任务上下文 | 两类业务分别的截止交付、任务收益 |
| S3 相近候选与波动 | 重叠区中相近均值、不同持续性与波动水平 | 风险修正与动态滞回 | 往返迁移、必要接续响应、稳定性/响应折衷 |

先对 S1/S2/S3 分别验证环境实现，再组合压力；避免一次叠加全部变化而无法解释效果。

## S1：让预测处理可预测的变化

使用与网络链路有关的空间衰减场，或可测量且具有持续性的外部业务变化。保留相关的公共分量，同时引入基于 site/link 标识的不同分量，记录相关长度与强度。其种子、流量生成和物理过程不依赖接入算法动作。

变化时间尺度需同时覆盖 0.1/0.3/0.5 s 预测时域及更长的持续退化。具体强度和相关长度在物理开发阶段根据测得的变化幅度、可用性和业务后果确定。白噪声不能作为“可预测变化”的替代物；纯突发且无历史征兆的事件应单独报告。

当前阴影模型各 RAT 共用同一个空间场，需先扩展链路标识。仅增加现有 `shadow_db` 或使用 abstract 的 `--stress` 都不能直接实现上述物理场景。

验证：检查实际 PHY/探测观测中的相关性、失效前预警长度及预测误差。分别报告全程与变化区间的预测误差、目的地排序正确率和失效后恢复次数。额外记录安全保留当前网络是否避免了短时迁移，并用实际包服务判定其代价。

## S2：建立真实的属性取舍

让至少两个候选在业务相关指标上互有优劣。例如一条链路容量充足但排队延迟易超过遥测截止，另一条容量受限但能够稳定满足遥测；图像业务上升时，二者取舍会改变。

通过 ns-3 中实际发送的独立背景流量和队列竞争生成这种状态。不能直接改写候选分数或规定哪个网络应被选中。背景过程使用固定种子和调度，与算法无关；被选链路的 payload 仍会改变其自身队列，这是需要记录的闭环作用。

当前容量为 SINR/带宽/回传上限的估计，不直接表示背景流量下的剩余可服务容量；加入真实负载后，需要同步说明和校验这一观测语义。探测延迟也不能被当作完整 payload 排队的直接替代。

比较学习权重、手工任务权重、均匀权重和熵权；保持预测、融合和共享控制一致。任务上下文的贡献可用另一个明确命名的上下文消融检验。评价优先依据实际包截止交付，服务估计仅用于解释机制。

## S3：同时检验稳定性和必要响应

在多个候选可用的重叠区引入具有物理/流量来源的分数接近与波动。包含短暂优势和持续优势，变化发生位置、幅度、持续性都由场景过程生成，不按 LAAVHA 的分数阈值摆放。

对照至少包括固定滞回 LAAVHA、完整 ALERA、只开风险修正、只开动态滞回。先固定 ALERA 是否采用增量统计、是否包含速度动态窗口，并让源码与论文完全一致。

记录有效阈值、窗口和风险扣分，检查它们是否真的改变迁移；分数有所变化但动作相同也需要如实记录。针对接收消失后的 SINR 旧值，记录观测年龄和有效标志。

## 对照与消融安排

主比较保留 task TOPSIS、moving average、linear trend 和修正后的不同 MADM/Fuzzy 方法。保留一致的物理可用性条件、中断模型、业务、随机环境和截止测量。

| 对照/消融 | 改变项 | 保留项 |
|---|---|---|
| 去预测分支 | 当前观测替代预测，关闭前视持续性 | 学习权重、共同控制 |
| 去预测融合 | 融合中不用未来值，持续性检查仍开启 | 预测持续性、学习权重、共同控制 |
| 去预测持续性 | 关闭目的地持续性检查 | 预测融合、学习权重、共同控制 |
| 固定任务权重 | 两组预先声明的任务权重替代学习权重 | 预测、持续性、共同控制 |
| 均匀/熵权替代 | 只替换权重规则，分别命名 | 预测、持续性、共同控制 |
| ALERA 分量消融 | 单独关闭风险项或动态滞回 | 相同基础 LAAVHA 与共同控制 |

排序规则与共享控制分开诊断。各方法阈值/窗口在相同预算的开发搜索中校准；可给出统一设置下的比较作为补充，但不能把相同数字阈值当成相同行为强度。纯排序无确认版本仅用于说明控制层作用，不替代带稳定机制的强对照。

## 指标与事件定义

业务指标采用实际 payload：遥测按时交付率、图像按时交付率与有效吞吐、最终未接收、晚到、迁移中断丢失。延迟分位数只对最终收到的包计算，并与违约率同时呈现。

行为指标包括原始迁移数、A→B→A 往返事件、短暂中间接入、失效恢复迁移、迁移前后的服务违约。往返事件的时间阈值与短暂驻留阈值需要在正式评测前冻结，并附阈值敏感度；往返不自动等于无用迁移。

切换时机需明确参考：是首次有效优势、共同服务失效还是提前采集的独立校准计划；三者分别命名。保持旧日志中的 `zero_delivery_cohort_s` 为零按时交付生成窗口累计时长，不改称物理失联时长。

独立 DP 只对其明确的服务抽象精确。新场景不预设应切换两次；参考计划允许任意网络顺序和次数，结合真实包重放评价其服务后果。

## 开发与测试安排

1. 完成公式与控制边界的数值验收，先不启动物理实验。
2. 实现场景与观测诊断，固定新的版本和输出目录，检查外生过程与算法无关。
3. 取得用户对物理开发运行的授权后，使用明确的开发种子做少量机制验证，再确定参数。已有 200/201 已被用于诊断，记录其已查看状态；场景调整后的确认性结论需使用新的未参与开发种子。
4. 新环境若不同于现有八个平滑训练任务，应在训练种子内覆盖相应变化，并使用分离的验证任务选择 checkpoint。最终测试数据不进入训练或归一化拟合。
5. 冻结算法、场景、权重训练、阈值选择规则和最终测试种子清单后，才能进行正式批跑。是否增加重复次数根据配对差异与不确定性确定。

开发阶段先看环境是否产生真实服务权衡、观测是否足够、模块是否实际介入。模块无增益时继续定位其适用范围或实现问题，保留相关结果。
